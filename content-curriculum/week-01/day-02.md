# Day 2: 判断ログの構築 — 思考プロセスの可視化

## この日のゴール

自分の判断プロセスを「記録できるもの」に変換する。
思考OS構築の第1歩は、判断のデジタルツインを作ることである。

## なぜ記録から始めるのか

個人の思考を他者やAIと同期するには、まず自分の判断を
言語化・構造化して共有可能な形にする必要がある。

記録されていない判断には、次の3つができない。

- **振り返り**: なぜその判断をしたか、後から検証できない
- **パターン抽出**: 成功判断の共通要素・失敗判断のバイアスが見えない
- **接続**: 他者が判断の根拠を読めない → 属人化のまま

## 判断ログの形式

1件の判断を、次の要素で記録する。

```yaml
# 判断ログの記録形式（1件分）
decision: 認証処理を自前実装からライブラリ移行へ
why: 保守に月8時間超かかり、移行2週間で元が取れるため
considered: [自前継続, ライブラリ移行, 部分移行]
weight: セキュリティ実績 > 機能 > 学習コスト
predicted: 移行後も機能低下なし、2週間で完了
result: ""  # 判断から1ヶ月後に追記する
```

ポイントは3つである。

1. **判断の理由**（why）: 結論でなく理由を残す。理由が残っていない
   判断は、後に「なんとなく」に落ちる
2. **重視した情報**（weight）: 何を優先したか。ここに自分の判断の
   クセが現れる
3. **結果の追跡**（result）: 予測（predicted）と実際を突き合わせる
   ための空欄を最初から用意する

## ワークショップ: 5W1H分解

直近1ヶ月の自分の重要判断を1つ選び、5W1Hで分解してから
上の形式でログに記録する。

| 観点 | 問い |
| --- | --- |
| What | 何を判断したのか（決断の内容） |
| Why | なぜその選択か（理由と根拠） |
| Who | 誰が関わるか（影響を受ける人） |
| When | いつ判断し、いつ効果が出るか |
| Where | どの文脈か（プロジェクト・制約） |
| How | どう実行するか（最初の一歩） |

エンジニアの技術判断（アーキテクチャ選定・ライブラリ導入・
リリース判断）が最も記録しやすい対象である。

## 判断前の3分間振り返り

記録と並行して、**判断の前に**3分間だけ自分に問う習慣を作る。

- 今の判断は、事実と願望のどちらに基づいているか
- 反対意見を1つ想像できるか
- 1ヶ月後にこの判断をどう評価していそうか

これはバイアス検出の最初の訓練である。ログの `weight` と
照らすと、自分が「重視したつもりの基準」と「実際に動かした基準」
のズレが見えてくる。
